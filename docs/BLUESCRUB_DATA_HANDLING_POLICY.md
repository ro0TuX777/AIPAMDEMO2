# BlueScrub — Data Handling Policy (G9)

> **Gate item**: G9 · **Status**: proposed
> **Governs**: retention, secret handling, purge access, audit
> **Plan reference**: [BLUESCRUB_DACV_IMPLEMENTATION_PLAN.md](BLUESCRUB_DACV_IMPLEMENTATION_PLAN.md) §13, §17 items 25–26

BlueScrub stages offensive tooling source, compiled binaries, git history, and — transiently — the
plaintext secrets those artifacts contain. This is the most sensitive data the platform holds.

---

## 1. What already exists

`aipam.prune_old_jobs` runs daily via Celery beat and calls
[`cleanup_old_jobs`](../backend/app/services/cleanup.py#L15), deleting the **whole job** — `jobs` row
plus job directory — once `created_at` exceeds `aipam_job_retention_days` (default 30). `Finding`
cascades.

**BlueScrub does not change this.** Platform retention stays platform retention. BlueScrub adds a
*finer-grained, earlier* sweep for its own high-sensitivity paths, and moves the state that must
outlive a job into tables with no job foreign key (see
[BLUESCRUB_DATA_CONTRACTS.md](BLUESCRUB_DATA_CONTRACTS.md) §0).

Durability summary:

| State | Lifetime | Mechanism |
|---|---|---|
| Plaintext secrets in raw scanner output | ≤ 72 h | `quarantine/` sweep |
| Staged source and binaries | ≤ 30 d from last project scan | BlueScrub sweep |
| Derived-job extracted files | ≤ 14 d | BlueScrub sweep |
| Findings, evidence, per-job scores | Platform `aipam_job_retention_days` (30 d) | existing `cleanup_old_jobs` |
| **Triage decisions** | Indefinite | `bluescrub_triage_ledger`, no FK |
| **Frozen baselines** | Indefinite | `bluescrub_baselines`, `job_id` is `SET NULL` |
| **Score history** | Indefinite | `bluescrub_score_history`, no FK |
| Audit records | Indefinite | `bluescrub_audit` |

## 2. Retention tiers

| Path | Default | Variable | Clock |
|---|---|---|---|
| `quarantine/` | **72 hours** | `AIPAM_BLUESCRUB_RETENTION_QUARANTINE_HOURS` | Job completion |
| `input/source/`, `input/binaries/` | **30 days** | `AIPAM_BLUESCRUB_RETENTION_SOURCE_DAYS` | **The project's most recent scan**, not this job's upload |
| `extracted_files/` on `re_assessment` child jobs | **14 days** | `AIPAM_BLUESCRUB_RETENTION_EXTRACTED_DAYS` | Job completion |

**Why the source clock is project-relative.** An absolute per-job clock purges the staged tree of an
actively-scanned project the moment the *first* scan ages out, silently destroying the incremental cache
and forcing a full re-scan on a project someone is working on weekly. Ad-hoc jobs with no `project_id`
fall back to job completion time.

**Why short retention is safe.** Purging staged source does not destroy findings — evidence, snippets,
severities, and scores live in the database. What is lost is the inline source viewer for old jobs,
re-scan without re-upload, and cache warmth. That is a convenience cost, not evidence loss. The one
thing that genuinely must outlive everything — analyst triage — is in the ledger.

### 2.1 Sweep mechanism

A new Celery beat task `aipam.bluescrub_retention_sweep`, hourly, alongside the existing
`aipam.prune_old_jobs`. Hourly rather than daily because the quarantine tier is measured in hours.

The sweep:
1. Deletes expired paths, never whole jobs — job deletion stays the platform's business.
2. Records `retention.purge` in `bluescrub_audit` with paths and byte counts.
3. Sets `metrics_json.dacv.artifacts_purged_at` so the UI can explain a missing source viewer instead of
   erroring.
4. Is idempotent and safe to run concurrently with `prune_old_jobs`; a missing directory is not an
   error.

Failed and cancelled jobs are swept on the next run regardless of tier — a job that never completed has
no analytic value and its staged input is pure liability.

## 3. Secrets

The database, API, UI, logs, and exports **never** hold a complete secret.

```jsonc
{ "secret_type": "api_key", "masked_value": "abcd…wxyz",
  "fingerprint": "hmac-sha256:…", "file": "config.py", "line": 42 }
```

- `masked_value`: first 4 and last 4 characters, ellipsis between. Secrets shorter than 12 characters
  are masked entirely.
- `fingerprint`: `HMAC-SHA256(key, secret_plaintext)`, hex. A **keyed** MAC, not a bare digest — many
  secret formats are structured and low-entropy, so a plain hash is reversible by enumeration.
- Plaintext exists only in scanner output inside the sandbox, and only until normalization. It is then
  deleted, or moved to `quarantine/` when an operator has to confirm a value during false-positive
  triage.
- Log statements must never interpolate a scanner's raw match. Enforced by a lint rule over
  `bluescrub/` and by a test that runs a fixture containing a canary secret and greps the entire log
  output for it.

### 3.1 Key custody

`AIPAM_BLUESCRUB_SECRET_HMAC_KEY`, 32 random bytes, base64. Generated by the deploy script into the
same `.env` that holds `aipam_api_token`, mode 0600. Backed up with deployment secrets; losing it is
equivalent to rotating it.

Environment rather than a file path is a deliberate, documented compromise: env values are visible via
`/proc/<pid>/environ` and `docker inspect`, but the key's only job is preventing fingerprint enumeration
by someone with database read and no host access — and on a single-VM air-gapped deployment those are
the same principal. Consistency with `aipam_api_token` beats a marginal gain against a threat this
deployment does not have.

### 3.2 Missing key — masked, but not fingerprinted

The gate said a missing key means secret scanners refuse to run. The intent —
never write an unkeyed digest, because a structured 20-character secret is
reversible by enumeration — is met more usefully by masking without a
fingerprint. The operator still learns a credential is present, which is the
finding they need; what they lose is deduplication of that secret across scans.
Refusing to run would have withheld the finding too, protecting nothing. The
count is reported as `secrets_without_fingerprint`.

### 3.3 Rotation

**Only on suspected key compromise. Never scheduled.**

Rotation is **permanently lossy and cannot be undone**: re-fingerprinting requires the plaintext
secrets, and those were deliberately destroyed at normalization. Every previously-triaged secret finding
reappears as new.

Required behaviour on rotation:

1. Write `secret_hmac.rotate` to `bluescrub_audit`.
2. Trend rendering reads those rows and draws a discontinuity marker at the boundary, so the jump in
   open Attribution findings is visibly a key change rather than a real regression.
3. The startup check warns if the key is absent and **refuses to run secret scanners** rather than
   falling back to an unkeyed digest.

## 4. Access control

AIPAM has no user or role model. Authentication is a single shared bearer token (`aipam_api_token`
via `verify_token`), so every caller is the same principal. Rather than invent an identity system,
BlueScrub reuses the existing second-tier pattern established by `aipam_kb_admin_token`.

| Operation | Required |
|---|---|
| Read reports, findings, trends | `aipam_api_token` |
| Triage, baseline set, wordlist edit | `aipam_api_token` |
| Single-job purge | `aipam_api_token` |
| **Project-wide purge** | `AIPAM_BLUESCRUB_ADMIN_TOKEN` via `X-BlueScrub-Admin-Token` |
| **Legal-hold set/clear** | `AIPAM_BLUESCRUB_ADMIN_TOKEN` |
| **Read `quarantine/` plaintext** | `AIPAM_BLUESCRUB_ADMIN_TOKEN`, and every read is audited |

When `AIPAM_BLUESCRUB_ADMIN_TOKEN` is unset, these operations are open to any valid API token —
identical to how `aipam_kb_admin_token` already behaves. Consistency matters more than a stricter
default that would surprise an operator familiar with the KB endpoint.

### 4.1 Legal hold

A project may be marked held. Held projects are exempt from the BlueScrub sweep. They are **not** exempt
from `cleanup_old_jobs`, because BlueScrub does not modify platform cleanup — so a hold preserves staged
artifacts and the durable tables, not the job rows. This limitation is documented rather than worked
around; changing it means changing platform retention, which is a separate decision.

### 4.2 The limit of the audit trail

With no authenticated identity, `bluescrub_audit.actor` and `bluescrub_triage_ledger.decided_by` are
**self-asserted strings**. The audit trail records what happened and what the caller claimed to be. It
is not proof of who acted.

This is stated in the operator guide and surfaced in the UI wherever audit data is displayed. An audit
table that implies more assurance than the auth layer provides is worse than no audit table, because it
invites reliance it cannot support.

## 5. Acceptance

1. A canary secret planted in a fixture repo appears nowhere in the database, API responses, exported
   PDF/HTML/CSV, or any log file — only its mask and fingerprint.
   *Implemented in `redaction.py`, which runs centrally between suppression and
   canonicalization so a new detector cannot leak by forgetting to opt in.
   Suppression runs first because it needs the plaintext to tell a real
   credential from `password = "changeme"`. Two secrets that mask identically
   stay distinct: `AKIA1111NARY` and `AKIA2222NARY` both render as `AKIA…NARY`,
   so fingerprints are taken over the keyed HMAC rather than the mask —
   otherwise two leaked credentials merge into one finding.*
2. Quarantine contents are gone within one sweep interval of the 72-hour boundary.
3. Staged source for a project scanned weekly is never purged; staged source for a project last scanned
   40 days ago is.
4. A cancelled job's staged input is purged on the next sweep regardless of tier.
5. Purging staged source leaves findings, scores, and triage intact and queryable.
6. Triage survives deletion of every job for the project by `cleanup_old_jobs`.
7. A frozen baseline survives deletion of its source job; `job_id` becomes null and the snapshot
   resolves.
8. With `AIPAM_BLUESCRUB_ADMIN_TOKEN` set, project-wide purge without the header returns 403 and is not
   performed.
9. Missing HMAC key ⇒ secret scanners refuse to run; no unkeyed fingerprint is ever written.
10. Every purge and every quarantine read writes an audit row.
11. A UI view of a job whose artifacts were purged renders an explanatory state, not an error.
